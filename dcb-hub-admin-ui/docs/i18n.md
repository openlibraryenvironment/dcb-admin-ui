# Translations

Every user-facing string goes through `react-i18next` — including `aria-label`, error
text and empty states. This is about the three ways that goes wrong and which gate
catches which.

## Accessible names are prose too

`eslint-plugin-i18next`'s default mode is `jsx-text-only`, which skips any literal whose
direct parent is a `JSXAttribute` (verified in
`node_modules/eslint-plugin-i18next/lib/options/defaults.js`). So the rule that exists
to stop hard-coded prose cannot read the attributes where prose is read aloud. Measured
before the fix: nine hits in eight files, no false positives. Four `aria-label`, two
`alt`, two `title`, and one `aria-label={cond ? "Logout" : "Login"}`, which was also
a WCAG 2.5.3 Label in Name failure, because the visible label beside it was translated.

`eslint.config.mjs` closes that with three `no-restricted-syntax` selectors on the
name-bearing attributes:

- **Three selectors, not one descendant match.** `aria-label={String(t("nav.x"))}`
  contains a `Literal` too, so a descendant selector would flag every translation key.
- **All-caps values are exempt**, mirroring the plugin's own `words.exclude` default:
  `label="CSV"` is a file format, not prose. Not exempting them cost 2 of the 9 hits.
- **Test files are exempt.** A fixture's label is the input to an assertion, not a
  string a user reads.
- `alt=""` for a decorative image is still allowed.

## A key that does not exist

i18next renders an unresolved key as the key itself, so a user sees
`libraries.accounts.email` where a label should be. Nothing fails; the page just reads
like a stack trace.

The application's i18next config sets `saveMissing` and a `missingKeyHandler` that
records to `window.__I18N_MISSING__`. Two gates read it:

- **Every e2e test.** `e2e/fixtures/test.ts` has an auto fixture that fails any test
  which rendered a missing key — in a dialog, a validation message, an error, a tab, on
  any route the test reaches, across every navigation. Every spec imports `test` from
  there; ESLint's `no-restricted-imports` rejects `test` from `@playwright/test` in
  `e2e/`, so a new spec cannot skip it.
- **Every route's first render.** `e2e/i18n-missing.spec.ts` walks
  `e2e/fixtures/routes.ts`, including routes no journey opens.

Both see only what the suite renders. Unit tests cover what can be checked without
running it:

- **`translationKeys.test.ts`** — every key written out in full, on every path: the
  argument of a `t()` call, a `<Trans i18nKey>`, or a `…Key` property such as `labelKey`.
  It found a Cancel button reading `ui.action.cancel` in a dialog no journey opens.
- **`navigationTargets.test.ts`** — every crumb of every route in the route tree, which
  builds its keys from the path.
- **`hostLmsClientConfig.test.ts`** — every `…Key` a Host LMS profile names.

A key built at runtime from data, such as `` `patron_request.statuses.${status}` ``, is
only checked where a journey renders it.

Three details that make the runtime collector a gate rather than a formality:

- **`missingKeyHandler` replaces the backend's own `saveMissing`** (i18next 23.11.5,
  `Translator.translate`), so nothing is posted anywhere. No network, no write.
- **It is a build-time switch**, `VITE_I18N_REPORT_MISSING`, read from
  `import.meta.env` and never from the injected runtime config — so it cannot be turned
  on against a deployed artefact. `playwright.config.ts` sets it for the e2e build.
- **The collector arms itself at boot**, creating the array before any key is missed,
  and the spec checks for that first. Without it, "no missing keys" would pass
  identically on a build where nothing was recording — which is the one failure a gate
  must not have.

### What it found on its first run

Two defect classes, on three routes:

- `nav.libraries.<uuid>.accounts` — `getBreadcrumbKey` has a `switch` per library tab
  and falls back to `"nav." + pathArray.join(".")`. `accounts`, `branding` and
  `insights` had no case, so the breadcrumb rendered that string literally, UUID
  included. Now cased, with a test per tab, because the fallback fails silently by
  construction.
- `Alpha Test Library` — the same function returns the record's own name where the crumb
  _is_ the record, and `Breadcrumbs` passed it to `t()`. That asks i18next for a key
  named after the library, on every page load. `isTranslationKey` now tells the two
  apart.

### What the every-test fixture found

Eight on its first run, all on `main`, none visible to the route walk:

- Four more breadcrumb fallbacks — `/hostlmss/new`, `/groups/<id>/insights`, and
  `/setup` and its chapters. Setup hides its crumbs, but the router's location moves
  before the page being left unmounts, so clicking the Setup tab rendered
  `nav.setup › nav.setup.discovery` for the transition.
- `hostlms.config_fields.renewal_limit_av` — a Host LMS field naming a key in the wrong
  namespace.
- Three sentences of `StaffRequest` alert text, passed to `<Trans>` as if they were keys.
  The user saw the right words only through i18next's fallback.

## A string translated too early

`i18n.t()` that runs while a module loads is fixed in the language, and from the
catalogue, that exists at that moment. A later language choice never reaches it, and a
catalogue that arrives afterwards leaves a raw key. Nothing fails: in en-GB, which is
bundled and loaded first, the string is right.

So a string is translated where it is used:

- **Grid columns** are built by a function that takes `t`, called inside
  `useMemo(() => getXColumns(t), [t])`, so they are rebuilt when the language changes
  and at no other time.
- **`valueOptions`** is a function the grid calls when it shows the options.
- **Validation messages** are functions the validator calls when validation fails:
  `{ error: () => i18n.t(…) }` in zod, `() => i18n.t(…)` in yup. A schema is module
  scope, so it uses `i18n.t` rather than a hook's `t`, but only inside the function.

**`src/i18nLoadTime.test.ts`** parses every source file and fails on an `i18n.t()`
reached at load: called directly, inside a function of the same file that is called at
load, inside an eager array callback (`map`, `filter`, …), or `i18n.t` handed to another
function. It does not follow a call into another module, nor a `t` destructured from
`i18n`, nor an immediately invoked function; none of those occur in `src` today.
`src/schemas/validationLanguage.test.ts` switches language after the schemas load and
checks a message follows.

On its first run it found 95 strings: the headers of five grids, the status and workflow
filter options, and the messages of the consortium, library and group schemas. Under a
Spanish choice they stayed English. It then caught the local holds limit message on its
first contact with the New Library wizard.

It checks _when_ a string is translated, not _whether_ it is: a `headerName: "Patron
barcode"` literal passes it, and is English in every language.

## A key nobody uses

`npm run i18n:unused` reports unused keys. **Its output is not a deletion list.**

There are 231 places that build a key at runtime — `t(\`theme.themes.${name}\`)`,
`t(\`settings_inheritance.level.${row.source}\`)` — and a static matcher cannot see
through a template literal, so every runtime-reached key is reported unused. Of the 842
reported keys that can be attributed to a namespace, **472 sit in namespaces that build
keys at runtime**:

| Namespace    | reported unused | runtime-built keys |
| ------------ | --------------: | -----------------: |
| `hostlms`    |             159 |                  1 |
| `insights`   |             140 |                  9 |
| `ui`         |              78 |                  0 |
| `requesting` |              76 |                  0 |
| `mappings`   |              59 |                  0 |
| `consortium` |              54 |                  2 |
| `libraries`  |              50 |                  5 |
| `theme`      |              24 |                  7 |
| `setup`      |              23 |                  1 |
| `locations`  |              22 |                  2 |

Deleting the reported list would ship missing-key fallbacks — visible raw key strings.

**So the order is: fix missing first, then sweep unused.** The missing-key gate above is
the measurement; a namespace with no runtime-built keys (`ui`, `requesting`, `mappings`,
`data_change_log`, `patron_request` — roughly 255 keys) can be swept on the static
report alone. The rest needs the runtime evidence.

There is deliberately **no gate on unused keys**. A key that does not exist is a
user-visible defect; a key nobody uses is housekeeping, and gating housekeeping at a
number nobody has verified is how a gate gets disabled.
